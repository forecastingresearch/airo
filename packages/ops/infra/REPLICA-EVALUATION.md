# Evaluate a cold rebuild of the forecasting deployment

Give a second operator or agent a clean controller, a reviewed commit, access to the target platform, a private inventory and a dated restore bundle. Start the clock before the first host exists. The operator should be able to create the deployment, verify it and recover a deliberately failed publication using those inputs. After capture, the incumbent must be able to keep serving without the candidate reading anything from it.

## Access the evaluator needs

Record the provider, resource scope, identity or vault item reference, and the result of each access test in the private installation record. Supply credentials to the relevant service identity. Keep keys, cookies, connection details and evidence outside git.

| Capability | Scope of the grant | Test |
| --- | --- | --- |
| Create the environment | Create and remove two hosts, their private network and appropriately sized volumes in a dedicated replica project. Administer those guests via verified SSH and sudo. | Create tagged empty hosts and volumes, verify host keys, reboot and reconnect. Check free bytes and inodes for restore plus a candidate release. |
| Recover the data | A source-side operator can capture a consistent checkpoint. Give the evaluator read and decrypt access to a replica restore bundle. Give the candidate a separate writable backup repository. | List both role snapshots, restore by ID, and recover a candidate backup into a fresh destination. Keep the incumbent backup outside the candidate's write scope. |
| Read code and dependencies | Read the private repo at the recorded SHAs, read commit checks, fetch OS/Python/npm dependencies and the pinned Node archive. | From the forecast service account, clone, inspect checks and run toolchain preflight. Exercise the normal release builder with a checked commit reachable from main. |
| Serve each endpoint | Manage replica DNS or private routing, ingress and TLS. Read the access-policy configuration and mint replica reader and per-site publisher identities. Include any forwarding hop on the live route. | Test from a reader's network and from the unattended publisher. Verify TLS hostname and trust, redirect or login flow, public access where intended, and protected downloads with anonymous, invalid and valid credentials. Exercise certificate renewal on the replica domain. |
| Reach upstreams | Configure the candidate service's proxy, allowlists and trust roots. Supply scoped identities for the enabled panel, research, economic data and round sources as appropriate. | Test through the service's actual environment. Use keyless probes, read-only requests and recorded provider responses for the rehearsal. Record live authentication and quota as unproven wherever a probe cannot establish them. |
| Alert and submit | Deliver to a test pager and use a test submission prefix with its own uploader. A monitor outside the two hosts needs read access to the replica endpoints and heartbeat. | Observe a test page, a stopped heartbeat and a stale-data alert. Exercise validation and upload-only retry against the test destination, including existing identical objects and a deadline failure. |
| Promote later | A separate grant covers live traffic routing, scheduler enablement, provider spend, the live pager and the real submission destination. | Record who can switch each control and reverse it, and how the sole active scheduler and uploader will be verified. |

An authorized source operator can prepare the bundle for the evaluator. In particular, access to an encrypted restic repository plus its password can expose full snapshots. Use a separately prepared, encrypted, data-only bundle when production credentials are outside the evaluator's scope. The restore helper's staging exclusions apply during extraction.

Apply network rules by role. The controller needs administrative SSH to the candidate hosts. The forecast service needs SSH to the assigned web receiver and HTTPS to its approved source and provider endpoints. Readers reach the web ingress over HTTPS. Exercise the release-check, Epoch, FRED, research/news, and ForecastBench storage routes that are in scope for the recorded jobs. Keep real-data replica endpoints within the agreed audience. A private replica DNS zone or test client routing can exercise the full hostname and TLS path before a public DNS change.

## Freeze a reference

Capture the following at a named UTC checkpoint. Record both role snapshot IDs and confirm the selected publication on each reader-facing endpoint matches the reference. If a deploy, job or transfer crosses the capture, reconcile the receipts and reselect a consistent point.

- Record the **independently deployed** code commit, frontend commit, data snapshot, current and previous release per project. From the frozen copies, produce a sorted list of relative paths, sizes and SHA-256 hashes for every published file. Keep that reference independently of the candidate.
- Inventory the paths, ownership and symlink targets, the shared panel, instrument inputs, results, attempts, database state, licensed assets, job receipts and saved ForecastBench rounds including upload receipts. Use a consistent database snapshot or include its required journal. Record what is expected for each installation, including empty datasets.
- Record job definitions at each selected release, active timer and service settings, enabled markers, routing and access policy, backup schedule and alert destinations by reference. Record any agreed change, such as the new paid and data workers, and its acceptance test.

Two details require an explicit migration choice. The role generates roots as `runtime_parent/NAME`; compare this with every source root before restoring. Absolute release links and virtualenv entry points need the original layout or a tested relocation and dependency rebuild. Also, a staging restore excludes runtime homes. Prepare saved round history and other required non-secret operational state from those homes separately. Verify the resulting coverage before accepting the bundle.

## Acceptance on the candidate

1. **Rebuild.** From the fresh controller create both hosts, apply pyinfra, restore real saved state, reapply and reboot. Exercise each site's origin and normal operator launcher after reboot. Keep live submission, paging and paid execution fenced from the replica. The PR's synthetic drill is a preliminary check. Put any hand-applied host fix into the provisioning recipe or the declared private inputs and repeat from clean hosts.
2. **Compare delivery.** First verify the restored releases with their native probes. Then exercise the candidate tooling at the pinned PR revision on isolated hosts. An install of the exact PR commit through the normal production release gate requires that commit to be checked and reachable from main. Once the selected releases support it, run `dashboardctl status --verify-content --json`. Independently compare the served bytes of every manifest entry, including assets, with the checkpoint. Exercise the existing AIRO ingress contract, the EEAI gate and the RSI public route, including legacy forwarding wherever used. A hash match between the candidate and its own web host alone cannot establish parity with the original.
3. **Operate it.** Deploy a checked frontend with the saved forecast data, verify the retained data and downloads, roll back, and recover a deliberate publication failure. Validate a data rebuild from saved inputs. Replay overlapping jobs, worker interruption, restart and duplicate ticks with provider-free fixtures under the candidate service accounts. Verify job IDs, single claims, missed-start rules and alert delivery. Exercise saved-round recovery under test date and destination controls.
4. **Record the verdict.** Deliver one private report with the input SHAs and snapshot IDs, access checks, source-to-candidate manifest differences, operation receipts, restore time and outstanding integrations. Mark each item passed, failed or untested. Independently confirm that production still owns all live side effects. A missing grant is an explicit open item.

## Promotion and the former environment

After approval, take a final reconciled checkpoint and drain old work. Fence the old scheduler and uploader, sync the final delta, verify the candidate's public bytes and access gates, switch traffic, then enable the reviewed schedule on its sole owner. Observe the first normally scheduled jobs, public verification, backup and any deadline-bound submission; record the actual evidence windows. Retain the previous serving snapshot and a tested traffic reversal. Before reversing job ownership, reconcile work and receipts created since the switch.

Keep the former environment available through the agreed observation window. To retain it as staging, assign it separate routing, service credentials, test destinations and backup storage, and disable live schedules. To retire it, verify restoration from an independent backup, then revoke its machine grants and remove the old routes and resources.
